# Jarvis 可信个人 Agent 底座设计规格

- 日期：2026-07-12
- 状态：用户已批准
- 目标平台：Windows 10/11 x64 桌面版
- 后续形态：可迁移到随身设备或便携硬件的个人 Agent

## 1. 产品定位

Jarvis 的长期定位不是单纯的录音转写工具，而是一个持续理解个人日常、保留可追溯记忆并辅助行动的个人 Agent。它通过用户明确启动的声音采集了解当天发生的对话、人物、主题、决定、承诺和待办，再形成会话总结、每日回顾和未来几天的建议计划。

当前里程碑先把桌面录音版做成可信底座。成功标准不是页面数量，而是建立一条不会静默丢数据的链路：

```text
麦克风 / 电脑系统声音
        ↓
本地音频证据与连续时间线
        ↓
持久化处理任务
        ↓
完整转写 → 说话人分离 → 长期人物身份
        ↓
事实 / 主题 / 决定 / Todo / 总结 / 规划建议
        ↓
每一项都能追溯到转写和原始音频时间
```

## 2. 当前问题与设计动机

对当前代码、数据库和本机录音目录的盘点显示：

- `jarvis.db` 中有 9 次会话、208 个音频分片和约 12,148 秒音频。
- 数据库只有 12 条转写，最近两次长录音有音频但没有转写。
- 208 个音频分片的 `transcription_status` 全部仍为 `pending`。
- 只有 2 次会话有最终总结；已有总结、Memory、Topic 和 Todo 可以持久化。
- 已保存的转写全部没有长期人物归属，`person_id` 为空且标签为 `mic`。
- 当前存在声纹录入和说话人识别代码，但没有形成从会话聚类到长期人物的可验证闭环。
- 当前 60 秒 WAV 分片是安全落盘机制，但界面把底层分片直接暴露给用户，没有提供连续会话播放体验。
- 麦克风恢复主要覆盖成功启动后的掉线，首次启动失败仍被压缩成模糊错误。
- 自动分析依赖实时转写；实时转写为空时，最终分析会失败且没有音频补转写任务恢复它。

根本问题是音频保存和实时转写是两条松散链路。新设计将音频证据设为唯一事实来源，实时转写只负责低延迟预览，后台任务负责最终完整性。

## 3. 里程碑范围

### 3.1 包含

- 手动开始、暂停、继续和结束录音。
- 三种采集模式：仅麦克风、仅电脑系统声音、麦克风与电脑声音同时采集。
- 麦克风和电脑声音两条独立音轨、同一会话时间线。
- Windows 系统声音正式采集，首选 WASAPI Loopback，失败时使用 Chromium Loopback。
- 实体麦克风选择、持久化选择、掉线独立恢复和虚拟设备自动回避。
- 音频证据安全落盘、哈希校验、明确缺口和持久化任务队列。
- 实时转写、后台补转写、中英混合质量控制和转写修订历史。
- “我”的声纹绑定、会话内多人分离、长期人物命名和跨会话候选识别。
- People、Topics、Todos、Memory 的长期存储和证据链接。
- 会话总结、每日回顾以及未来几天的建议计划。
- 连续会话播放器、分轨试听、同步转写和证据跳转。
- 现有录音、转写、总结和记忆的非破坏迁移与补处理。
- 为未来随身硬件保留稳定的音频输入协议。

### 3.2 不包含

- 隐藏录音、开机自动录音或未经用户明确启动的监听。
- 手机端或随身硬件成品。
- 云端多设备同步。
- 只捕获某一个 Windows 应用的声音；首版采集 Windows 整体输出。
- 自动修改日历、发送邮件、发消息或代表用户联系他人。
- 没有证据支持的主动决定。
- 在严重混响、远距离收音或多人同时说话时承诺百分之百识别准确。

## 4. 核心设计原则

1. **证据优先。** 音频先落盘，转写、认人和总结都可以稍后完成。
2. **失败隔离。** 一条音轨、一个处理任务或一次云请求失败，不能破坏其他录音证据。
3. **最终一致。** 实时结果可以不完整，但后台必须把每个已提交音频分片处理到完成或可见失败状态。
4. **可追溯。** 事实、决定、承诺、Todo 和建议必须能够返回来源转写及音频时间。
5. **可修订。** 转写、身份和 AI 结果保留版本，不能覆盖原始证据。
6. **精确优先于强行识别。** 低置信度人物保持未知，不能为了覆盖率污染长期声纹库。
7. **本地身份、云端匿名。** 真实姓名和声纹留在本地，MiniMax 只接收必要文本和匿名人物编号。
8. **面向硬件的边界。** 下游只依赖标准音频帧和会话事件，不依赖 Electron 麦克风实现。

## 5. 总体架构

### 5.1 输入适配层

所有音频来源实现统一 `AudioSource` 契约：

- `sourceType`：`mic` 或 `system`；未来允许 `wearable`。
- `sourceId` 和设备描述。
- PCM 格式、采样率和通道数。
- 会话 ID、音轨 ID、连续序号。
- 单调时钟采集时间和墙上时钟时间。
- 启动、帧到达、暂停、恢复、结束、缺口和错误事件。

桌面首版包含：

- `MicAudioSource`：实体麦克风和明确选择的虚拟麦克风。
- `WindowsSystemAudioSource`：Windows 整体输出的 Loopback 采集。

未来硬件只需产生同一契约的音频帧和事件，不需要复制桌面 UI 或 MiniMax 逻辑。

### 5.2 Capture Engine

Capture Engine 是会话采集的权威协调器，负责：

- 创建会话和一条或多条音轨。
- 检查授权、磁盘空间、设备和模型准备状态。
- 独立控制每条音轨的启动、掉线、恢复和结束。
- 把 PCM 写入最多 60 秒的安全 WAV 分片。
- 为每个分片计算哈希并原子提交元数据。
- 记录没有音频的明确时间区间，不生成伪造静音。
- 在分片提交后创建持久化处理任务。

60 秒分片继续作为底层安全机制。暂停、设备中断、切换和结束允许生成不足 60 秒的首尾分片。UI 不把这些分片表现为独立 Memory。

### 5.3 Evidence Store

SQLite 和录音目录共同构成证据库。数据库保存会话、音轨、分片、缺口、处理任务、转写版本和证据关系；文件系统保存 7 天内的原始 WAV。

音频分片是处理链的权威输入。实时转写不是唯一来源，也不能作为“已经处理音频”的证明。

### 5.4 Processing Workers

处理任务按依赖关系运行：

1. `transcribe_chunk`：从已提交 WAV 生成最终候选转写。
2. `reconcile_transcript`：把实时预览与后台结果按音轨和时间合并。
3. `diarize_track`：在音轨内生成说话人聚类和人数。
4. `resolve_identity`：把会话说话人匹配到“我”或已确认人物。
5. `analyze_session`：生成主题、记忆、决定、Todo、建议和最终总结。
6. `daily_digest`：按本地日期汇总已完成会话，生成每日回顾和后续规划建议。

任务状态、重试次数、依赖、输入哈希、模型版本和下一次重试时间全部持久化。应用重启后恢复到期任务，不能只在内存中保存状态。

### 5.5 Memory Graph

长期记忆由人物、主题、事件、Todo、会话和证据组成。AI 不能直接执行 SQL；所有结果先通过结构校验、证据校验、去重规则和版本规则，再写入派生表。

## 6. 麦克风与系统声音分轨采集

### 6.1 采集模式

开始录音前提供三个明确选项：

- 仅麦克风。
- 仅电脑声音。
- 麦克风与电脑声音同时采集。

系统声音默认关闭，每次由用户明确选择开启。录制期间主窗口和任务栏持续显示 `MIC`、`PC` 两条来源的独立状态。

### 6.2 Windows 系统声音

复用现有 OpenWhispr 会议录音能力：

1. 首选进程内已有的 WASAPI Loopback helper。
2. helper 不可用或启动失败时回退 Chromium `getDisplayMedia` Loopback。
3. 只读取音频轨，不保存屏幕图像或视频。
4. 首版捕获 Windows 整体输出，不提供逐应用选择。

### 6.3 双轨同步

麦克风与系统声音分别写入独立音轨和独立 WAV 分片。每个帧和分片都携带统一会话时间，播放器和转写按时间对齐。

音轨启动时间不同、设备切换或时钟漂移不会通过填充假音频掩盖，而是通过时间戳和 `audio_gaps` 明确表示。播放器按时间线渲染每条音轨。

### 6.4 回声和重复内容

系统输出可能从扬声器重新进入麦克风。新设计：

- 原始两轨都保留，不能为了去重破坏证据。
- 转写层通过时间重叠、文本相似度、能量相关性和现有 AEC 能力识别重复内容。
- 被判定为回声的片段保留修订记录，但默认只在统一转写和 AI 输入中出现一次。
- 低置信度重复候选不自动删除，而是标为待确认。

### 6.5 独立恢复

双轨模式下两条来源独立运行：

- 初始启动必须明确显示两条来源是否成功。若一条失败，用户选择重试或降级继续，不能静默降级。
- 运行期间某一轨掉线，另一轨继续录制。
- 失败轨重新枚举设备并无限重试；恢复后继续同一会话。
- Windows 输出设备改变后重建 Loopback 音轨并记录缺口。
- 仅系统声音模式在初次无法取得系统音频时不创建空录音会话。

## 7. 会话状态与故障恢复

### 7.1 生命周期

会话状态：

- `preparing`：检查授权、设备、磁盘和模型。
- `recording`：至少一条选定音轨正在采集。
- `degraded`：会话仍录制，但一条选定音轨正在恢复。
- `paused`：用户暂停，当前分片已封存。
- `finalizing`：关闭所有来源并提交尾片和清单。
- `processing`：录音已安全完成，后台任务仍运行。
- `ready`：最终转写和会话分析完成。
- `recovered`：上次异常退出后恢复的会话。
- `failed`：录音未能建立或证据写入出现不可恢复失败。

“录音已保存”和“AI 已完成”是两个独立状态。用户结束录音后，Jarvis 先确认音频证据已经提交，再在后台继续完善转写和总结。

### 7.2 麦克风恢复

- 用户选定设备在初始启动和恢复时优先。
- 自动恢复排除 Sonar、VoiceMeeter、Steam、YY 等已知虚拟设备。
- 恢复前重新枚举设备，不复用过期设备列表。
- 运行中断后立即尝试，随后退避到每 10 秒一次并无限继续。
- 暂停、结束或退出时取消重试并丢弃晚到的流。
- 初始权限拒绝是可操作的致命错误，不进入无意义重试。

### 7.3 持久化任务恢复

Worker 使用租约领取任务。应用退出或进程崩溃后，过期租约回到 `retry`，下次启动继续处理。相同输入哈希和任务类型具有幂等约束，重复启动不会生成重复结果。

### 7.4 可操作错误

UI 不再只显示 `Recording could not continue`。错误包含：

- 阶段：准备、打开设备、建立音轨、写文件、转写、说话人、云分析。
- 来源和设备：`MIC / Shure MV7`、`PC / WASAPI Loopback`。
- 浏览器、Windows 或 Worker 错误代码。
- 当前是否仍在录、是否已经安全保存。
- 重试次数、下一次重试时间和用户可执行操作。

## 8. 转写完整性与中英混合质量

### 8.1 实时预览与最终转写

- 实时转写用于 Today 页面低延迟显示，标为 `provisional`。
- 每个音频分片提交后都产生后台补转写任务。
- 后台结果按音轨和时间生成 `final` 转写版本。
- Reconciler 只在完整新版本提交后替换显示版本，避免先删后写造成空白。
- 所有替换保留旧文本、来源、时间、模型和原因。
- 结束录音必须刷新最后一段实时文本，但最终完整性仍由 WAV 任务保证。

### 8.2 中英混合策略

- 使用支持中文和英文的本地 Whisper 模型，不强制单一语言。
- 保留双语上下文提示和用户自定义词典。
- 对姓名、产品名、缩写和专有术语使用会话词表及历史确认词表。
- 在每月 5–10 美元硬预算内，允许对低置信、高价值文本做云端纠错；云端失败不阻塞本地转写。
- 纠错结果保留原文、当前文本、置信度和原因，不能删除原始文本。

### 8.3 完成定义

会话转写只能在以下条件下标为完成：

- 所有仍存在的音频分片都有成功转写、明确无语音结果或可见阻塞状态。
- 没有未登记的 `pending` 分片。
- 最后音频时间已经被最终转写覆盖或明确标为无语音。
- 两轨重复内容已经完成去重判断。

## 9. 说话人与长期人物身份

### 9.1 两层模型

必须区分：

- **会话说话人聚类**：本场的 `speaker_1`、`speaker_2`，只描述音频中的不同声音。
- **长期人物**：`self`、张三或尚未命名人物，跨会话保持稳定。

转写片段先关联会话聚类，再通过可修订链接关联长期人物。不能直接把一次聚类 ID 当作永久人物 ID。

### 9.2 “我”的声纹绑定

- 首次引导录制约 30 秒。
- 从三个不重叠、有效语音窗口分别提取 embedding。
- 保存原始样本引用、质心、embedding 模型版本和更新时间。
- 录入完成后进行自相似性检查；不一致时要求重新录入。

### 9.3 会话内多人分离

- 实时聚类提供临时标签。
- 后台按整场音轨和跨分片重叠窗口重新聚类，生成最终人数和时间线。
- 麦克风轨和系统声音轨分别聚类，再在人物层建立可能的同一人关系。
- 多人重叠、短语音和低信噪比片段允许保持未知或重叠状态。

### 9.4 长期人物匹配

人物匹配按 embedding 模型版本校准阈值。自动关联必须同时满足：

- 至少 12 秒有效语音。
- 至少 3 个互不重叠的有效窗口。
- 最佳候选达到该模型在留出评测集上满足不低于 95% 精确率的阈值。
- 最佳与第二候选的差距达到同一评测确定的安全 margin。

结果分级：

- 高置信度：可自动关联已验证人物，并显示置信度来源。
- 中置信度：显示“可能是张三”，等待确认。
- 低置信度：保持“说话人 2”。

用户把“说话人 2”改名为“张三”时，默认保存为长期人物并锁定本场对应聚类；UI 允许取消“以后识别这个人”，仅修改本场。

未确认片段不能更新声纹质心。只有用户确认的聚类才可以成为新的可信样本，防止错误自我强化。

### 9.5 隐私

真实姓名、声纹和人物关系只保存在本地。发送 MiniMax 时使用 `self`、`person_2` 等会话匿名编号。

## 10. 四层长期记忆

### 10.1 L1：证据层

- 音频分片和缺口。
- 最终转写及修订历史。
- 说话人时间线和身份链接。

证据层不能被 AI 输出覆盖。

### 10.2 L2：事件层

- `fact`：对话明确表达的事实。
- `decision`：已经做出的决定。
- `commitment`：人物明确承诺的事情。
- `opinion`：人物表达的观点。
- `todo`：明确行动项。
- `suggestion`：Jarvis 的建议，不能自动升级为事实或承诺。

事实、决定、承诺和 Todo 必须包含至少一个有效转写证据。主体或证据不清晰时进入 `needs_confirmation`。

### 10.3 L3：关系层

人物、主题、项目、会话和事件形成可查询关系。相同事情的处理规则：

- 完全相同的规范化主题自动合并。
- 相似事件只建立候选关系，不在证据不足时强制合并。
- 重复提及增加出现次数并更新最近时间。
- 新决定通过 `supersedes` 指向被替代的旧决定，旧记录仍可查看。
- 相互冲突的事实同时保留并标记待确认。

### 10.4 L4：Agent 层

- 会话增量摘要和最终摘要。
- 当天人物、主题、决定、承诺和 Todo 时间线。
- 未完成事项、期限冲突和需要追问的问题。
- 基于已有证据的明后几天安排建议。

首个里程碑只生成建议草案，不自动修改日历或替用户发送消息。

每日回顾在本地日期改变后、应用首次运行时为前一天调度，也允许用户手动重新生成。如果当天仍有未完成转写，报告明确显示为“部分完成”，处理完成后再生成最终版本。

## 11. 数据模型

在现有 SQLite 表基础上增加幂等迁移。

### 11.1 会话与音轨

`sessions` 增加：

- `capture_mode`：`mic`、`system`、`dual`。
- `processing_state` 和 `timeline_version`。
- `finalized_at`、`ready_at`。

新增 `audio_tracks`：

- `id`、`session_id`、`source_type`。
- `device_id`、`device_label`、`strategy`。
- `sample_rate`、`channels`、`started_at`、`ended_at`。
- `state`、`model_clock_origin`。

`audio_chunks` 增加：

- `track_id`、`sequence_number`、`source_type`。
- `write_state`、`transcription_state`。
- `deleted_at` 和文件可用状态。

音频过期后删除文件但保留元数据 tombstone、哈希和时间范围，使转写证据仍能定位到原会话时间。

新增 `audio_gaps`：

- `track_id`、开始和结束时间、原因、恢复次数。

### 11.2 处理任务

新增 `processing_jobs`：

- `id`、`session_id`、`track_id`、`chunk_id`。
- `job_type`、`state`、`priority`。
- `input_hash`、`input_version`、`model_version`。
- `attempt_count`、`next_retry_at`。
- `lease_owner`、`lease_expires_at`。
- `error_code`、`created_at`、`completed_at`。

相同业务输入和任务类型具有唯一约束。

### 11.3 转写和身份

`transcript_segments` 增加：

- `track_id`、`source_type`。
- `version`、`result_kind`：`provisional` 或 `final`。
- `speaker_cluster_id`、`quality_flags`、`model_version`。

新增：

- `speaker_clusters`：会话内聚类、有效语音时长和质心。
- `cluster_person_links`：长期人物候选、置信度、状态和模型版本。
- `voice_profile_samples`：已确认人物的多个可信声纹样本。

### 11.4 记忆

现有 `session_summaries`、`topics`、`todos`、`memories` 和证据表继续使用，并增加：

- 版本、生成模型和输入哈希。
- `supersedes_id`、确认状态和冲突状态。
- 对所有高影响条目的证据完整性约束。
- `daily_digests` 保存每日回顾及其覆盖会话和版本。

## 12. 桌面用户体验

### 12.1 Today

顶部显示：

- 采集模式、麦克风设备、系统声音策略。
- `MIC` 和 `PC` 独立状态与音量。
- 录音时长、暂停和结束操作。
- 音频最近落盘时间。
- 转写完成比例、待补分片数量。
- 识别人数、待确认人物数量。
- 最近分析时间和新增 Todo。

中间显示实时转写，右侧显示当前主题、决定、Todo 和待确认人物。实时结果明确标为处理中，不伪装成最终完整转写。

### 12.2 Memory

Memory 以会话为单位，而不是音频分片为单位。详情页包括：

- 一条连续时间线，展示麦克风轨、电脑声音轨和缺口。
- 单听麦克风、单听电脑声音或混合播放。
- 同步转写；点击句子跳转对应时间。
- 说话人标签、候选人物和改名入口。
- 总结、主题、决定、Todo 和“查看来源”。
- 音频过期后仍保留转写和证据时间，但显示原音频已删除。

### 12.3 People、Topics 和 Todos

- People 展示“我”的录入状态、人物确认状态、最近互动、共同主题和证据。
- Topics 展示相关会话、人物、状态变化、决定和未完成事项。
- Todos 展示负责人、期限、来源会话和证据；AI 不能自动完成 Todo。

## 13. MiniMax 与云端预算

- MiniMax 只接收稳定转写、匿名说话人编号、必要旧记忆和允许引用的 segment ID。
- 不上传原始音频、声纹、真实姓名或 API Key。
- 每月硬预算限制保持在 5–10 美元。
- 网络错误、429 和可重试 5xx 使用持久化退避。
- 鉴权失败和额度耗尽不无限重试；UI 显示阻塞原因。
- 云分析失败不能阻止录音、转写、播放和本地搜索。
- 所有模型输出经过结构、长度、类型和证据 ID 校验。

## 14. 保留、删除和安全

- 麦克风与系统声音原始音频默认保留 7 天。
- 转写、总结、人物、主题、Todo 和长期记忆长期保存。
- Retention Cleaner 删除文件后保留音频元数据 tombstone，不破坏证据时间线。
- 删除完整会话时删除其音轨、转写和独占证据；由其他会话共同支持的记忆保留其他证据。
- MiniMax Key 使用 Electron 安全存储，日志不记录 Key、转写全文、真实姓名或音频内容。
- 系统声音采集需要明确开启，录制期间持续可见。

## 15. 现有数据迁移

迁移必须非破坏、可回滚、可重复：

1. 关闭写入并备份 `jarvis.db`、`transcriptions.db` 及 WAL/SHM 文件。
2. 在事务中执行幂等 schema 迁移。
3. 为现有音频分片创建默认 `mic` 音轨和连续 sequence。
4. 保留现有转写、总结、Memory、Topic 和 Todo，标记为 legacy 版本。
5. 为仍存在的旧 WAV 创建补转写任务。
6. 对目录名可匹配现有 session ID 的录音进行校验后关联。
7. 无法关联数据库的 WAV 不删除，进入“待恢复录音”，等待用户确认。
8. 迁移完成后运行行数、外键、文件存在性和哈希抽样校验。
9. 校验失败时恢复备份，不启动部分迁移后的应用。

已有总结不因升级自动消失。重新分析生成新版本并保留旧版本来源。

## 16. 测试与验收

### 16.1 录音可靠性

- Shure MV7 和 Arctis Nova Pro 均可被选择并跨重启记住。
- 仅麦克风、仅系统声音和双轨三种模式都能开始、暂停、恢复和结束。
- 双轨连续录音至少 2 小时。
- 麦克风连续断开和恢复至少两次，会话不结束且不选择 Sonar 等虚拟设备。
- 系统输出设备切换后系统音轨恢复，同一会话继续。
- 一轨掉线时另一轨继续，缺口可见。
- 强制退出并重启后，已落盘证据和未完成任务恢复。
- 每个提交分片的哈希可验证，没有未登记文件或静默丢失。

### 16.2 系统声音和去重

- 麦克风静音时，Teams、Zoom、浏览器视频和本地播放器声音可以单独录制和转写。
- 双轨模式下可分别回放 MIC 和 PC。
- 扬声器外放造成的重复声音不在统一转写和总结中重复出现。
- 去重不删除原始两轨证据。

### 16.3 转写

- 100% 已提交音频分片具有 `pending`、`running`、`completed`、`retry` 或 `blocked` 明确状态。
- 标记为 ready 的会话没有遗留 pending 分片。
- 结束、暂停、掉线和重启场景不丢最后一句。
- 补转写和实时转写合并后没有重复句段。
- 中英混合近讲评测目标：中文 CER 不高于 15%，英文 WER 不高于 20%，自定义姓名和术语召回率至少 90%。
- 噪声评测单独记录，不把低质量文本写成高可信长期事实。

### 16.4 说话人与人物

- 受控 2–4 人数据集评测人数和片段归属。
- “我”的自动归属精确率至少 95%。
- 已确认人物跨会话自动关联精确率至少 95%。
- 中低置信度结果保持候选或未知，不强制命名。
- 改名、撤销、合并和声纹重新录入都有测试。
- 未确认片段不能更新声纹质心。

### 16.5 记忆和 AI

- 100% 的事实、决定、承诺和 Todo 引用允许的转写证据。
- 每条证据可以定位到会话、音轨和音频时间。
- 相同输入重复运行不生成重复 Memory、Topic 或 Todo。
- AI 不能自动完成 Todo。
- 新决定保留被替代的旧决定。
- 无效 JSON、未知证据、超长输出和错误类型被拒绝且不污染派生表。
- MiniMax 失败不影响录音和本地数据。

### 16.6 迁移与打包

- 在当前真实数据库副本上运行迁移，验证现有 9 次会话和所有已知派生数据不丢失。
- 对现有 WAV 执行补转写演练。
- 启动、关闭和再次启动验证持久化。
- 主进程测试、renderer 测试、typecheck、lint、i18n、构建、Windows 打包和便携版启动全部通过。

## 17. 实施阶段边界

本规格描述一个完整里程碑，但实施必须拆成四个连续、可独立验收的阶段：

1. **证据与双轨采集底座。** 完成数据库迁移、音轨/分片/缺口/任务模型、麦克风诊断与恢复、Windows 系统声音和双轨安全落盘。这个阶段不依赖新的 AI 功能即可验收。
2. **完整转写与连续会话。** 完成后台补转写、实时/最终结果协调、双轨去重、任务恢复、处理状态 UI 和连续播放器，并对现有录音执行补处理。
3. **说话人与长期人物。** 完成“我”的声纹绑定、整场聚类、人物候选、确认/撤销/合并和跨会话识别评测。
4. **证据化记忆与 Agent 输出。** 完成长期记忆版本、主题、Todo、会话总结、每日回顾和未来几天建议，并确保所有高影响输出可追溯。

每个阶段只有在自身测试、迁移检查和打包验证通过后才进入下一阶段。阶段之间共享本规格的数据契约，不允许后续阶段绕过音频证据和持久化任务队列建立旁路。

## 18. 发布判定

只有同时满足以下条件才发布新的桌面版：

- 两小时双轨硬件验收通过。
- 麦克风和系统声音独立恢复通过。
- 旧录音补转写和迁移验证通过。
- 会话连续播放器和证据跳转可用。
- “我”与至少一个已确认人物的真实跨会话验收通过。
- 所有长期事实和 Todo 证据校验通过。
- 打包版在不依赖开发目录的情况下启动并访问本地数据库、原生模块和模型。

本规格批准的是可信个人 Agent 的桌面底座。实现顺序、文件级改动和提交拆分在后续实施计划中确定。
